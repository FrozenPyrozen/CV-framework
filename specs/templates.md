# Templates Spec

Status: v1 · Applies to: `templates/<name>/`, `npm run template-import`, `/import-template`, `npm run render`

A template defines how a CV looks in Word and PDF. Content always comes from the CV Markdown, and the template contributes only formatting.

## 1. Folder

```
templates/<name>/
├── source.docx           # optional: the original file, only for your own CVs (never someone else's)
├── import-map.yaml       # the template-importer agent's paragraph labels (input to template-import)
├── template.docx         # formatting only: styles, numbering, page setup, header/footer, one sample of each paragraph type, no CV content
├── style-map.yaml        # how each Markdown element maps to the template
├── fixes.yaml            # renderer fixes for this template
├── reference-preview.png # the approved look of page 1, used by the layout reviewer
└── import-report.md      # findings from the import (written by the template-importer agent; classic predates it)
```

`<name>` is lowercase-kebab (e.g. `classic`, `modern-two-tone`).

## 2. `style-map.yaml`

Templates often use direct formatting (font size and color on each piece of text, lines drawn as shapes) rather than Word styles. So the map stores a **sample paragraph** for each paragraph type, which the renderer copies and fills. A named style is used only when the template really has one.

```yaml
schema_version: 1
name: classic
approved: true                     # set only after the user confirms the test build
approved_at: 2026-10-15            # date of that approval (optional, recorded with approved)
page: { width_twips: 12240, height_twips: 15840, margins_twips: { top: 580, bottom: 280, left: 720, right: 720 } }
fonts: [Cambria, Arial]            # every font the template uses; checked by doctor and pdf-check
links: { color: "1155cc", underline: true }
paragraphs:                        # paragraph type -> position of its sample paragraph in template.docx (classic's real map)
  name:            { sample: 0 }
  headline:        { sample: 1, bold: true }
  contact_line:    { sample: 2 }
  section_heading: { sample: 3 }
  section_rule:    { sample: 4, keep: true }     # drawn line under each section heading
  entry_title:     { sample: 5 }
  entry_details:   { sample: 6, date_tab: true } # dates after the sample's tab stop
  bullet:          { sample: 7 }
  body:            { sample: 8 }
  section_intro:   { sample: 9 }
  education_line:  { sample: 10 }
  skills_line:     { sample: 11 }
  # header_rule:   optional drawn line under the header; classic doesn't use it (it rendered as a stray dot and a large gap)
```

`template.docx` contains exactly these sample paragraphs, in this order. Each text sample holds a placeholder (`{{bullet}}`, `{{body}}` …) instead of CV text; `keep` samples (drawn lines) have no text. Required types: `name`, `contact_line`, `section_heading`, `entry_title`, `entry_details`, `bullet`, `body`. Optional types: `headline` (falls back to `contact_line`), `section_intro`, `education_line`, `skills_line` (fall back to `body`), `header_rule`, `section_rule` (skipped when missing). The style map is generated by `template-import`; the agent's labels live in `import-map.yaml` (section 4).

**Portfolio templates** (`kind: portfolio` in the style map; `specs/outputs/portfolio.md` 5) use the portfolio's paragraph types instead: required `cover_title`, `project_title`, `section_label`, `body`, `list_item`, `image`, `caption`, `section_heading`; optional `cover_name`, `cover_contact`, `headline`, `intro`, `project_meta`, `skills_line`, `contact_line` (falling back to `body`). `portfolio-classic` is generated by `npm run portfolio-template` (its original is a free-form Pages layout); the CV renderer refuses a portfolio template, and the portfolio renderer a CV template.

## 3. `fixes.yaml`

Known rendering problems of a template, applied by the renderer after filling. Each fix records why it exists:

```yaml
- id: bullet-indent-pages      # as in templates/classic/fixes.yaml
  why: "The original bullet indent (163/105 twips, tab at 162) renders with the text pushed about 0.6 inch right in Pages."
  found: "2026-10-15"
  set:
    bullet: { indent_left: 226, hanging: 226, tab: { type: num, pos: 226 } }
```

Supported fix types (each fix has `id`, `why`, `found`, `set`):

| `set` key | Effect |
|---|---|
| `bullet: { indent_left, hanging, tab }` | bullet indentation in the sample and the list definition (e.g. the Pages bullet fix) |
| `keep_with_next: [types]` | those paragraph types always move to the next page together with the following paragraph (no orphaned headings) |
| `date_tab: { align, pos }` | tab stop for the dates in entry detail lines (e.g. right-aligned at the margin) |
| `keep_first_bullets_together: N` | an entry's first N bullets stay together, and the line right before a run of bullets (entry details, an education line) stays with the first bullet, so a heading never ends a page with fewer than N bullets |
| `keep_last_bullets_together: N` | an entry's last N bullets stay together, so no bullet sits alone on a new page |
| `paragraphs: { <type>: { indent_left, first_line, before, after, line } }` | indentation and spacing per paragraph type in twips (20 = 1 pt; `line: 240` = single spacing); overrides the Word style |
| `first_after_section_heading: { before }` | space above whatever comes first under a section line, so every section starts with the same gap |
| `rule_full_width: true` | the drawn line under section headings (`section_rule`) spans the whole text width (page width minus the effective left and right margins, after any `page_margins` fix); combine with `paragraphs: { section_rule: { indent_left: 0 } }` so it starts where headings start |
| `page_margins: { top, bottom, left, right }` | page margins in twips (any of them), overriding the template's section settings |
| `sizes: { a4: { width_twips, height_twips, page_margins }, letter: { … } }` | (portfolio templates) the page sizes a template is built in, each with its page size and margins; one Word file and PDF per size (`specs/outputs/portfolio.md` 5) |
| `letter_spacing: N` | character spacing of N twentieths of a point on every run; `1` is invisible and stops Pages from forming fi/fl ligatures that some PDF readers extract wrongly |

## 4. Import (`/import-template <file> <name>`)

| Input | Method |
|---|---|
| Word (`.docx`) | `npm run template-import -- <file.docx> <name>` lists every paragraph (index, style, list/drawing/tab flags, text). The template-importer agent labels the types in `templates/<name>/import-map.yaml` (paragraph index per type, plus `keep`, `jc`, `size`, `bold`, `date_tab`), then `npm run template-import -- <file.docx> <name> --map templates/<name>/import-map.yaml` builds `template.docx` and `style-map.yaml`. One sample per type is kept and all other content removed. |
| PDF (not built yet; planned after `build` works end to end) | Extract fonts, sizes, colors, positions, margins and line spacing with `pdfjs-dist`. The agent compares them with a page preview, and the template is rebuilt as a new Word file with the `docx` npm package. Fine details may differ, and `import-report.md` lists them. |

### Rules

1. **Only formatting is kept.** Someone else's name, contacts and text are never saved, and their file is never copied into the repo. (Your own old CV may be kept as `source.docx`.)
2. **ATS warnings** in `import-report.md`: multi-column layouts, text boxes, layout tables, contact details only in header or footer, icons instead of words, image-only text, unusual fonts. When any apply, a one-column variant is offered.
3. **Fonts** are listed in `style-map.yaml`. `doctor` checks them by exporting a test PDF and reading which fonts are embedded.
4. **Test build:** the master CV (and its other market versions) is rendered with the new template into `.cv-runs/template-test-<name>/`, exported, checked with `pdf-check` and previewed (all pages), without touching the real CV's outputs or build record. The user approves, then `approved: true` and `approved_at` are set and `reference-preview.png` saved from that test build.
5. An unapproved template can be built with `--template <name>`, but `build:all` refuses it.

### `import-report.md` format

```markdown
# Import report: <name>
Source: <file name only> (Word | PDF) · Imported: <date>

## Paragraph types found
| Type | Sample | Notes |

## ATS warnings
- <warning>: <why it matters> -> <what the one-column variant does instead>

## Not copied exactly (PDF imports)
- <detail>

## Test build
Pages: N · pdf-check: pass/fail · Preview: preview/page-1.png …
```

## 5. Rendering rules

- Every Markdown element in the supported subset (`cv-spec.md` section 9) maps to one paragraph type: the header block to `name`, `headline`, `contact_line` (and `header_rule`); `#` to `section_heading` + `section_rule`; `##` to `entry_title`; `###` to `entry_details`; `*` to `bullet`; config intro lines to `section_intro`; lines in the education section to `education_line`; `**Label:** …` lines to `skills_line`; other paragraphs to `body`. Required types are checked at import; optional ones fall back as listed in section 2, and a missing fallback is reported as a render warning.
- Hyperlinks are created as new link entries from the URLs in the Markdown (profile links reach it through the generated header), never by reusing the template's own link ids.
- Bold Markdown becomes bold text in the same font, size and color as the sample.
- Dates in entry detail lines go after the sample's tab stop.
- `fixes.yaml`: fixes that change sample paragraphs or the list definition (bullets, tabs, spacing, keep-with-next, `rule_full_width`) are applied to the samples before filling; `page_margins` changes the section properties; fixes that depend on the filled document (bullet groups, the first item under a section line, letter spacing) are applied after filling.
- The current template, `classic`, is imported from `templates/classic/source.docx` (your previous CV) with `templates/classic/import-map.yaml`. Its look was then adjusted with the user through `fixes.yaml` and approved from all-page previews: on 2026-10-15 (aligned left edge, tighter spacing, right-aligned dates, headings and bullet groups kept together), 2026-10-16 (section lines aligned), 2026-10-20 (tighter header and sections) and 2026-10-21 (top margin 0.25 inch; the style map still records the template's original 580 twips).
