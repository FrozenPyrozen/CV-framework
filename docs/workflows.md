# Workflows (commands)

Open this file to find which agent file and scripts a workflow follows. Commands are Claude Code slash commands (`.claude/commands/`); any other tool runs the same workflow by following the agent file and the scripts listed. Each command file points to an agent definition (or one of its sections) or runs scripts, and never holds rules of its own. Script details: `docs/scripts.md`. Every workflow that changes files ends with `npm run verify -- --fast` while iterating and `npm run verify` before handing back.

| Command | What happens | Follow |
|---|---|---|
| `/add-repo <path or name> [--resume]` | The whole new-repo flow: `/harvest`, **pause for your approval of the summary**, `/compose`, **pause for your approval of the CV diff**, then `/variants` (ending with `build:all`) and `/review`; ends with the `/status` summary and the review verdicts. Progress is saved in a git-ignored `.cv-runs/<run-id>/state.json` (stage, repo, summary id, pending approvals); `--resume` continues the latest run. | `agents/harvester.md`, then `agents/composer.md`, `agents/tailor.md`, `agents/reviewer.md` |
| `/harvest <path or name> [id]` | Locate the repo (a path is stored as the repo name in the summary plus `name: path` in `framework.local.yaml`; a name missing on this laptop asks for the path; no remote URLs), find your commits (likely matches with `git_identities` are confirmed before they're added to `profile.yaml`; zero matches stops), ask new or existing job (likely matches by period and domain; a merge adds the repo to `repos`), ask the job details for a new summary one topic at a time with suggestions from the repo (nothing guessed), write or merge the summary, propose new tags and skills for approval, then `validate`, `lint` (which secret-scans the summary) and the diff. | `agents/harvester.md` |
| `/harvest-prompt [--merge <id>] [--out <file>]` | Portable harvest, step 1, for a repo that can't come to this laptop (plan 9c, `specs/work-summary-spec.md` 9): `npm run harvest-prompt` writes a self-contained prompt; you run it with any AI tool in that repo on the other machine, review the summary it writes and bring the file back. | `npm run harvest-prompt` |
| `/import-summary <file>` | Portable harvest, step 4: `npm run import-summary` checks the file with the same rules as `validate` plus the secret scan; the harvester asks about unknown tags and job details, adds a new summary or merges it (work-summary-spec 7), then `/compose` (and `/variants` after it, as for any summary change). | `agents/harvester.md` (Importing a portable summary) |
| `/import-docs <file…>` | Old CVs and portfolios as sources (plan 9d, `specs/sources-spec.md`, lowest precedence): `import-doc` keeps each file and its text; the advisor proposes per summary the gaps it fills, its numbers (in the CV only once confirmed) and its conflicts (the current value stays), goes through them with you, then hands over to the composer. | `agents/advisor.md` (/import-docs), then `agents/composer.md` |
| `/portfolio-material [summary-id…]` | The advisor goes through each project's images, links and demos (summary section 8) and asks which projects go into the public portfolio (`show_in_portfolio`, `portfolio_order`, `portfolio_label`, `portfolio_title`, `portfolio_projects`, each item's `project:`); nothing is public without your explicit yes; `validate` checks the items (plan 9e P1). | `agents/advisor.md` (/portfolio-material) |
| `/portfolio [summary-id or page-id…]` | `npm run portfolio -- refresh`, then the portfolio agent writes the projects `status` lists (keeping text from the published portfolio, sourced `doc:<id>`, or from that page's summary; an intro only when you ask), each sentence sourced, then `npm run portfolio -- check` (plan 9e P3). | `agents/portfolio.md` |
| `/compose` | The composer updates the master CV, then `npm run check`. | `agents/composer.md` |
| `/tailor --profile <id>` / `--jd <file or text> [--profile <id>] [--market <id>]` | Builds `cv/variants/<id>/cv.md` from the profile, or `cv/tailored/<company-role>/` for one job, always starting from a role profile (`--profile`, or the closest one the tailor proposes and you confirm; recorded as `profile:` in `jd-tags.yaml`); pasted job ad text is saved as `job-description.md` in that folder; then `npm run build` on it, with a gap report. | `agents/tailor.md` |
| `/align [--since <ref>]` | Checks that framework changes are aligned: `doc-check`, `index --check` and `npm run impact` first, then the auditor compares the changed code with the specs it touches and checks the plan, *Rules at a glance*, *Read first* lists, decisions in force, docs, acceptance scenarios and tests; writes `.cv-runs/align/<date-time>.md` and never edits. | `agents/auditor.md` |
| `/cover-letter <cv/tailored/company-role> [--market <id>]` | Writes `cover-letter.md` in a job folder from the tailored CV's sources (a source on every sentence, `jd` for the job ad), then `npm run cover-letter -- check` and `build` (Word, one-page PDF, check, preview). Needs `/tailor --jd` for that job first. | `agents/cover-letter.md` |
| `/variants` | Rebuilds every profile variant (after summaries or the master CV change), then `npm run build:all`. | `agents/tailor.md` |
| `/review [cv] [rubric…] [--jd <file>] [--market <id>] [--portfolio]` | Runs the reviewers (default all 6) on the chosen market version (default: the default market) into `reports/<date-time>/` (one report per rubric, `<rubric>-<cv>.md` when the run covers several CVs). ATS and HR read the market file, so hidden fields count as intended and HR questions fit the market. With `--jd`, ATS also scores the CV against that job ad. "Would this CV pass an AI ATS?" is `/review ats`, "…and then HR?" is `/review hr`. `--portfolio` reviews the public portfolio with the proofreading, fact-check, confidentiality and layout rubrics (plan 9e P6). Each reviewer reads its `review-context` bundle; ATS and HR for one CV may share one reviewer agent (two bundles, two reports), and proofreading, layout and ATS run on Sonnet while fact-check, confidentiality and HR keep the default model (`.claude/commands/review.md`). | `agents/reviewer.md` |
| `/improve [report…]` | The advisor goes through the findings one topic at a time with suggested answers, records them as facts, has the composer apply them and shows the diff. Findings you decline become decisions (e.g. "no LinkedIn link", "keep length"), so later reviews don't raise them. It first asks about any summary value still to confirm (`status` `CONFIRM` lines). | `agents/advisor.md`, then `agents/composer.md` |
| `/add-experience` | You describe experience in your own words; the advisor asks follow-up questions, writes a `confirmed.yaml` entry (or a `cv_entry` for a new job), and the composer adds the bullets. For that job, it also asks about a value still to confirm (`CONFIRM`). | `agents/advisor.md`, then `agents/composer.md` |
| `/profile` | You describe a change ("moved to Poland, new phone +48…"); the advisor asks the follow-ups (work permit, still B2B, time zone, relocation), updates `profile.yaml`, runs `/variants` (ending with `build:all`) and lists tailored CVs and sent PDFs that still have the old details. It also names the shared release when its text changed (`status` `SHARED` lines): share the new PDFs, then `npm run release`. | `agents/advisor.md` |
| `/job-change` | **Leaving:** first a **final harvest** of every repo of the job while you still have access (the summary is the only record afterward), then `period.end`, final results and metrics as facts, and whether the job stays in Experience. **Starting:** the new job as a `source: user` summary (role, company, dates, engagement, what you'll own), harvested later. Then `/variants`, `/status` and the sent CVs now outdated. Afterward it names the shared release if its text changed (`SHARED`). | `agents/advisor.md` |
| `/import-template <file> <name>` | Template import (`specs/templates.md` 4), then a test build and previews for your approval. | `agents/template-importer.md` |
| `/build [cv] [--market <id>] [--template <name>] [--no-pdf] [--entries-reviewed]` | `npm run build`, then reports the PDF checks and shows the page previews. | scripts only |
| `/status [--ack <company>]` | `npm run status`, then suggests the commands that bring stale CVs up to date, and explains `SENT` (a sent CV changed: `--ack`), `SHARED` (the shared release's text changed: share the new PDFs, then `npm run release`) and `CONFIRM` (a summary value to confirm: `/improve` or `/add-experience`) lines. | scripts only |
| `/log-application` | Records a sent CV in `facts/applications.yaml` (`specs/facts-spec.md` 5). | `npm run log-application` |
| `/doctor` | `npm run doctor`, then explains how to fix anything missing. | scripts only |
